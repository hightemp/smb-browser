# PRD: SMB Browser

## Название продукта

SMB Browser - кроссплатформенное desktop-приложение для управления сохраненными SMB-доступами и просмотра Microsoft Windows / Samba shared folders во встроенном файловом браузере на Qt Widgets.

## Краткое описание

Приложение позволяет пользователю вручную сохранять SMB-подключения, проверять их доступность и открывать содержимое SMB-шар внутри собственного интерфейса. Приложение не должно делегировать просмотр системному проводнику как основной сценарий: список файлов и папок должен загружаться через SMB-backend и отображаться собственной моделью Qt.

Основной технологический стек первой версии:

- Qt5 + C++.
- Qt Widgets для UI.
- CMake для сборки.
- SQLite для хранения метаданных.
- QtKeychain как основной механизм хранения секретов.
- Локальный encrypted vault с master password как fallback.
- libsmb2 как основной кандидат SMB-backend.
- Собственная `RemoteFileModel` на базе `QAbstractItemModel` или `QAbstractTableModel` для отображения SMB-файлов.
- Основной язык пользовательского интерфейса - английский; русский язык должен быть доступен как переключаемая локализация.

## Цели

- Дать пользователю единое место для хранения и организации SMB-доступов.
- Поддержать нормализацию разных форматов SMB-путей и учетных данных.
- Реализовать встроенный файловый браузер SMB без использования системного проводника как основной реализации.
- Обеспечить безопасное хранение паролей без plain text в SQLite.
- Сделать архитектуру расширяемой: UI, storage, secrets, SMB-backend и операции с файлами должны быть разделены.
- Все сетевые и длительные файловые операции должны выполняться асинхронно, с прогрессом и отменой.
- Сформировать тестируемое ядро: path normalization, repositories, credential storage contract, import/export, log sanitization, SMB error mapping, browser model и операции через fake backend.
- Поддержать локализацию UI: английский как основной язык и русский как дополнительный язык, переключаемый пользователем.

## Не-цели

- Не реализовывать сетевой стек SMB вручную.
- Не строить приложение вокруг Windows-specific API как основной реализации.
- Не монтировать SMB-шары в локальную файловую систему как обязательное условие работы.
- Не использовать `QFileSystemModel` для SMB-файлов.
- Не выполнять автоматическую проверку всех сохраненных подключений при запуске первой версии.
- Не реализовывать полноценный двухпанельный файловый менеджер в первой версии, если это задерживает основной сценарий.
- Не хранить пароли в SQLite в plain text.
- Не логировать пароли, токены, полные credential-строки, connection strings с секретами или другие чувствительные данные.

## Целевая аудитория

- Администраторы Windows / Linux / Samba окружений.
- Пользователи, которым нужно часто открывать разные SMB-шары с разными учетными данными.
- Support / DevOps / QA команды, работающие с файловыми шарами клиентов или стендов.
- Технические пользователи, которым нужен переносимый инструмент без ручного монтирования каждой шары.

## Поддерживаемые платформы

Первая версия должна проектироваться для современных:

- Windows.
- Linux.
- macOS.

Кроссплатформенность должна быть заложена на уровне архитектуры:

- Бизнес-логика не должна зависеть от платформенного UI или системных файловых менеджеров.
- SMB-доступ должен идти через абстракцию `SmbClient`.
- Платформенные различия keychain, уведомлений, tray и открытия локального файла должны быть изолированы в отдельных сервисах.
- Если часть функциональности недоступна на конкретной платформе, UI должен явно показывать это как ограничение, а не падать.

## Основные пользовательские сценарии

### US-001: Добавить SMB-доступ

Пользователь вводит название, путь, логин, пароль, домен или workgroup, комментарий, группу и признак избранного. Приложение нормализует путь, сохраняет метаданные в SQLite, пароль сохраняет в keychain или encrypted vault.

### US-002: Проверить доступность

Пользователь выбирает сохраненный доступ и нажимает "Check" в английском UI или "Проверить" в русском UI. Приложение показывает, доступен ли сервер, доступна ли шара, корректны ли учетные данные, есть ли права, не истек ли timeout, нет ли DNS или protocol error.

### US-003: Открыть SMB-шару во встроенном браузере

Пользователь выбирает подключение и нажимает "Подключиться". В центральной области приложения отображается список папок и файлов удаленной SMB-шары. Навигация происходит внутри Qt Widgets UI.

### US-004: Управлять файлами

Пользователь открывает папки, переходит назад, вперед и вверх, обновляет список, скачивает и загружает файлы, создает папки, удаляет, переименовывает, копирует и перемещает файлы внутри SMB или между SMB-шарами.

### US-005: Открыть файл

При двойном клике файл скачивается во временный кэш и открывается системным приложением. Для текста и картинок доступен встроенный preview как отдельный модуль.

### US-006: Импортировать и экспортировать подключения

Пользователь экспортирует список подключений без паролей по умолчанию. Экспорт паролей в plain text доступен только как опасная ручная операция с отдельным явным подтверждением.

### US-007: Работать через системный трей

Пользователь закрывает главное окно, приложение сворачивается в трей. Из трея можно открыть главное окно, выйти из приложения, увидеть быстрый список избранных подключений и получить уведомления об ошибках подключения.

### US-008: Переключить язык интерфейса

Пользователь открывает настройки и выбирает язык интерфейса: System, English или Russian. По умолчанию приложение использует English как основной язык, если системная локаль не поддерживается или пользователь не выбрал другое. Все основные окна, диалоги, предупреждения, ошибки и tray menu должны отображаться на выбранном языке.

## Функциональные требования

### FR-001: Список SMB-доступов

Приложение должно хранить список вручную добавленных SMB-доступов.

Поля подключения:

- ID.
- Название.
- Исходный путь, введенный пользователем.
- Нормализованный URI вида `smb://server/share`.
- Server.
- Share.
- Domain / workgroup.
- Username.
- Auth type.
- Ссылка на secret record в `CredentialStore`.
- Комментарий.
- Группа / категория.
- Признак избранного.
- Дата последнего открытия.
- Дата создания.
- Дата изменения.
- Последняя ошибка.
- Дата последней успешной проверки / подключения.

Поддерживаемые варианты ввода пути:

- `\\server\share`.
- `smb://server/share`.
- `server/share`.

Поддерживаемые варианты ввода пользователя:

- `DOMAIN\user`.
- `user@domain`.
- `user`.
- Anonymous / guest access.
- Current user, если это возможно кроссплатформенно или через abstraction layer.

### FR-002: Нормализация пути и учетных данных

Приложение должно нормализовать ввод пользователя перед сохранением.

Правила:

- `\\server\share` преобразуется в `smb://server/share`.
- `server/share` преобразуется в `smb://server/share`.
- `smb://server/share` сохраняется как canonical URI с нормализованными server/share компонентами.
- Server и share должны храниться отдельно от URI.
- Domain и username должны храниться отдельно.
- `DOMAIN\user` разбирается как domain = `DOMAIN`, username = `user`.
- `user@domain` разбирается как username = `user`, domain = `domain`.
- Auth type хранится отдельно и может принимать минимум: password, guest, anonymous, current user.
- Пароль никогда не должен попадать в normalized URI или SQLite.

Ограничения нормализации:

- Первая версия требует server и share.
- Подпапка внутри шары может храниться как optional initial path, если пользователь ввел более глубокий путь.
- Некорректные URI должны возвращать типизированную ошибку валидации.

### FR-003: CRUD и управление доступами

Пользователь должен иметь возможность:

- Добавить доступ.
- Редактировать доступ.
- Удалить доступ.
- Проверить доступность.
- Подключиться и открыть во встроенном браузере.
- Скопировать путь.
- Импортировать список доступов.
- Экспортировать список доступов.

Удаление должно требовать подтверждения, если запись содержит сохраненный секрет. При удалении подключения приложение должно удалить или пометить к удалению связанный secret record, если он не используется другими записями.

### FR-004: Проверка доступности

Проверка запускается только пользователем по кнопке "Check" или явным действием. В первой версии не выполнять автоматическую проверку всех записей при запуске.

Результат проверки должен различать:

- Сервер доступен.
- Сервер недоступен.
- Шара доступна.
- Шара недоступна.
- Неверный логин или пароль.
- Нет прав.
- Таймаут.
- Ошибка DNS.
- Протокол или версия SMB не поддерживается.
- Сетевая ошибка.
- Неизвестная ошибка.

Приложение должно обновлять:

- Последнюю успешную проверку.
- Последнюю ошибку.
- Визуальный статус выбранного подключения.

### FR-005: Встроенный файловый браузер SMB

Браузер должен работать внутри приложения и получать данные через `SmbClient`.

Обязательные операции:

- Открыть папку.
- Перейти назад.
- Перейти вперед.
- Перейти вверх.
- Обновить текущую папку.
- Скачать файл локально.
- Открыть файл через системное приложение.
- Создать папку.
- Удалить файл или папку.
- Переименовать файл или папку.
- Загрузить файл на SMB.
- Скопировать путь.
- Копировать и перемещать файлы внутри SMB.
- Копировать между разными SMB-шарами.
- Drag-and-drop из локальной системы в SMB.
- Drag-and-drop из SMB на рабочий стол.
- Множественный выбор файлов.
- Отображение прогресса операций.
- Отмена операций.

Открытие файла:

- Двойной клик по файлу скачивает его во временный кэш.
- После скачивания файл открывается системным приложением.
- Для текстовых файлов и изображений предусматривается встроенный preview.
- Preview проектируется как отдельный модуль `PreviewService`.

### FR-006: RemoteFileModel

Для SMB-файлов должна использоваться собственная модель `RemoteFileModel`, а не `QFileSystemModel`.

Модель должна:

- Представлять remote entries: имя, тип, размер, дата изменения, атрибуты, права при наличии, remote path.
- Поддерживать сортировку и фильтрацию на уровне UI/model proxy.
- Корректно обновляться после операций create/delete/rename/upload/download.
- Не выполнять SMB-запросы напрямую из view.
- Работать с сервисным слоем и получать уже подготовленные данные.

### FR-007: Поиск и фильтрация

Приложение должно поддерживать:

- Фильтр по списку сохраненных доступов.
- Фильтр или поиск файлов в текущей папке.

Рекурсивный поиск по SMB-шаре является отдельным этапом и не блокирует первую версию. Он должен проектироваться с учетом отмены, прогресса, ограничения глубины и сетевой нагрузки.

### FR-008: Import / Export

Формат импорта и экспорта должен быть документирован и версионирован.

По умолчанию экспорт должен включать:

- Метаданные подключений.
- Нормализованные пути.
- Группы.
- Комментарии.
- Избранное.
- Даты и статусные поля, если это полезно.

По умолчанию экспорт не должен включать:

- Пароли.
- Токены.
- Данные keychain.
- Master password.
- Полные credential strings.

Экспорт с паролями в незашифрованном виде:

- Должен быть отдельной ручной операцией.
- Должен быть выключен по умолчанию.
- Должен требовать отдельного явного подтверждения.
- Должен показывать сильное предупреждение о риске компрометации.
- Должен быть покрыт тестами, которые подтверждают, что обычный экспорт не содержит паролей.

### FR-009: Логирование и журнал

Приложение должно писать логи в файл и показывать их в окне или панели журнала.

Логи должны проходить через `LogSanitizer`.

Запрещено логировать:

- Пароли.
- Токены.
- Master password.
- Полные credential strings.
- URI или строки, в которых есть секреты.
- Сырые ответы backend, если в них могут быть секреты.

Логи должны включать:

- Время.
- Уровень.
- Категорию.
- Сообщение.
- Correlation ID операции.
- Sanitized error details.

### FR-010: Системный трей

Приложение должно поддерживать системный трей:

- Закрытие окна сворачивает приложение в трей, если включена соответствующая настройка.
- Кнопка "Exit" реально завершает приложение.
- Из трея можно открыть главное окно.
- Из трея доступен быстрый список избранных подключений.
- Уведомления об ошибках подключения показываются через tray, если платформа поддерживает.

### FR-011: Темы

Приложение должно поддерживать режимы:

- System.
- Light.
- Dark.

По умолчанию используется System. Пользователь может изменить тему в настройках. Логика темы должна быть тестируемой отдельно от UI.

### FR-012: Локализация интерфейса

Основной язык приложения - английский. Русский язык должен быть доступен как переключаемая локализация.

Приложение должно поддерживать режимы языка:

- System.
- English.
- Russian.

Требования:

- Default language mode - English, если системная локаль не распознана или выбранный перевод недоступен.
- При выборе System приложение использует поддержанную системную локаль; для неподдержанной локали fallback - English.
- Пользователь может явно выбрать English или Russian в настройках.
- Все пользовательские строки должны быть подготовлены к переводу через стандартный механизм Qt i18n (`tr()`, `.ts`, `.qm` или эквивалентный Qt-friendly workflow).
- Нельзя зашивать user-facing строки напрямую в бизнес-логику, repositories, SMB-backend или credential layer.
- Ошибки должны хранить стабильный error code и локализуемое user-facing message отдельно от sanitized technical details.
- Переключение языка должно применяться без перезапуска там, где это практично; если для части UI требуется перезапуск, приложение должно явно сообщить об этом.
- Импорт/экспорт данных не должен зависеть от языка UI: формат, ключи и enum values остаются стабильными и англоязычными/машиночитаемыми.

## Нефункциональные требования

### Производительность

- UI не должен зависать при сетевых операциях.
- Открытие больших директорий должно быть инкрементальным или иметь явное состояние загрузки.
- Длительные операции должны иметь прогресс, статус и возможность отмены.
- Рекурсивные операции должны иметь ограничения, чтобы не создавать избыточную сетевую нагрузку.

### Надежность

- Ошибки SMB, DNS, authentication, permissions и timeout должны отображаться пользователю понятным образом.
- Частичные ошибки в batch-операциях должны быть видимы и не должны скрывать успешные элементы.
- Временный кэш скачанных файлов должен очищаться по политике приложения.
- Сбой keychain должен приводить к понятному fallback или ошибке, а не к потере данных.

### Расширяемость

- SMB-backend должен быть за интерфейсом `SmbClient`.
- Credential storage должен быть за интерфейсом `CredentialStore`.
- Storage метаданных должен быть за repository layer.
- UI не должен напрямую работать с SQLite, keychain или libsmb2.
- Модули должны иметь четкие границы ответственности.

### Тестируемость

- Core logic должна тестироваться без реального SMB-сервера.
- Для сценариев SMB должен использоваться `FakeSmbClient`.
- Интеграционные тесты с Docker Samba должны быть отдельным optional profile и отключены по умолчанию.
- UI smoke tests должны проверять базовое создание окон и основные flow.

### Совместимость

- Qt5 должен быть базовой версией UI-фреймворка.
- Код должен быть переносимым между Windows, Linux и macOS.
- Платформенные возможности должны быть изолированы за adapter/service layer.
- Локализация должна использовать переносимый механизм Qt и не зависеть от платформенных API.

## Безопасность и хранение секретов

### Основной credential store

Основной вариант хранения секретов - QtKeychain, использующий системные хранилища секретов:

- Windows Credential Manager на Windows.
- Keychain на macOS.
- Secret Service / KWallet и доступные backend на Linux.

SQLite хранит только metadata и reference ID секрета. Пароли не должны храниться в plain text в таблицах SQLite.

### Fallback credential store

Если системное хранилище недоступно, пользователь может включить fallback:

- Локальный encrypted vault.
- Master password, который не сохраняется в plain text.
- KDF для получения ключа из master password.
- Authenticated encryption для хранения секретов.
- Явное предупреждение о различии между системным keychain и fallback vault.

Точные криптографические примитивы должны быть выбраны на этапе технического дизайна с учетом доступных библиотек и кроссплатформенной поддержки. Самописная криптография запрещена.

### Работа с секретами в памяти

Приложение должно снижать риск утечки секретов:

- Не включать пароли в `QString`/логи/исключения без необходимости.
- Очищать временные буферы с секретами настолько, насколько это разумно для C++/Qt.
- Ограничивать время жизни объектов, содержащих секреты.
- Не передавать секреты в UI-модели, логи и telemetry.
- В диалогах использовать password fields и не сохранять историю ввода.

### Auth types

Минимальный набор типов аутентификации:

- Password.
- Guest.
- Anonymous.
- Current user.

`Current user` должен быть доступен только если выбранный backend и платформа поддерживают его через переносимую abstraction layer. Если поддержки нет, UI должен показывать режим как недоступный или experimental, а не обещать работу.

## Экспорт/импорт и риски незашифрованного экспорта паролей

Обычный экспорт должен быть безопасным по умолчанию и не содержать пароли.

Экспорт с plain-text паролями нужен для ручных сценариев миграции, но считается опасной операцией. UX должен включать:

- Отдельный пункт или checkbox "Включить пароли в экспорт".
- Выключенное состояние по умолчанию.
- Предупреждение перед экспортом, что файл будет содержать пароли в незашифрованном виде.
- Требование явного подтверждения пользователем.
- Рекомендацию хранить файл только во временном защищенном месте и удалить после переноса.
- Отдельное лог-событие без содержимого паролей.

Тесты должны подтверждать:

- Обычный экспорт не содержит парольные поля.
- Обычный экспорт не содержит known secret values.
- Логи экспортной операции не содержат секреты.
- Экспорт с паролями доступен только через explicit option.

## UI/UX требования

### Главное окно

Структура:

- Слева: список сохраненных SMB-доступов и групп.
- Сверху: поиск/фильтр и основные кнопки.
- Центр: файловый браузер текущей SMB-папки.
- Снизу: статус подключения, последняя ошибка, прогресс операций.
- Отдельное окно или панель журнала.
- Системный трей.

Основные кнопки:

- Add.
- Edit.
- Delete.
- Check.
- Connect.
- Import.
- Export.

В русской локализации эти действия должны отображаться как "Добавить", "Редактировать", "Удалить", "Проверить", "Подключиться", "Импорт", "Экспорт".

### Состояния UI

UI должен явно показывать:

- Нет выбранного подключения.
- Подключение выполняется.
- Директория загружается.
- Ошибка подключения.
- Пустая папка.
- Операция выполняется.
- Операция отменена.
- Операция завершилась с ошибкой.

### Диалоги

`ConnectionDialog` должен поддерживать:

- Ввод пути в разных форматах.
- Ввод username/domain в разных форматах.
- Выбор auth type.
- Поле пароля только для password auth.
- Комментарий, группу, избранное.
- Preview нормализованного URI.
- Валидацию до сохранения.

`SettingsDialog` должен поддерживать:

- Тему System / Light / Dark.
- Язык интерфейса System / English / Russian.
- Настройки tray behavior.
- Настройки логирования.
- Настройки credential store.
- Настройки временного кэша.

### Язык и локализация

- Все тексты основного UI должны исходно проектироваться на английском языке.
- Русский перевод должен покрывать основные пользовательские сценарии первой версии: connections list, dialogs, browser, operations, errors, settings, logging viewer, tray menu, import/export warnings.
- Локализация не должна менять сохраненные данные пользователя, normalized URI, IDs, enum values, формат экспорта или значения в SQLite.
- Для длинных русских строк UI должен иметь достаточную ширину, переносы или elision, чтобы текст не ломал layout.
- Новые user-facing строки должны добавляться через translation workflow, а не напрямую как непереводимые literals.

### Доступность и usability

- Основные операции должны быть доступны через context menu.
- Для опасных операций delete/export passwords нужны подтверждения.
- Ошибки должны быть понятными пользователю и пригодными для диагностики.
- UI не должен блокироваться на сетевых вызовах.

## Архитектурные решения

### Общая структура

Приложение разделяется на слои:

- Presentation: Qt Widgets, models, dialogs, view controllers.
- Application services: orchestration use cases, validation, operation queue, transfer manager.
- Domain/core: value objects, normalized paths, error model, DTO, interfaces.
- Infrastructure: SQLite repositories, QtKeychain store, encrypted vault, libsmb2 implementation, platform adapters.

### Модули

Ожидаемые модули:

- `App / bootstrap` - инициализация приложения, зависимостей, настроек, логирования.
- `MainWindow` - композиция основного UI.
- `ConnectionsPanel` - список доступов, группы, фильтр, действия над подключениями.
- `RemoteBrowserWidget` - навигация и toolbar файлового браузера.
- `RemoteFileModel` - модель remote entries для Qt views.
- `ConnectionDialog` - добавление и редактирование подключений.
- `SettingsDialog` - настройки темы, языка, tray, storage, logging, cache.
- `LogViewer` - просмотр логов внутри приложения.
- `TrayController` - системный трей и tray menu.
- `ThemeManager` - применение темы и хранение выбранного режима.
- `LocalizationManager` - выбор языка, загрузка переводов и применение локали UI.
- `ConnectionRepository` - доступ к SQLite metadata для подключений.
- `SettingsRepository` - настройки приложения.
- `CredentialStore` - интерфейс хранения секретов.
- `QtKeychainCredentialStore` - primary реализация.
- `EncryptedVaultCredentialStore` - fallback реализация.
- `SmbClient` - интерфейс SMB-операций.
- `Libsmb2SmbClient` - реализация на libsmb2.
- `FakeSmbClient` - тестовая реализация.
- `TransferManager` - upload/download/copy/move и временный кэш.
- `OperationQueue` - очередь операций, progress reporting, cancellation.
- `PreviewService` - preview текста и изображений.
- `PathNormalizer` - нормализация путей и учетных данных.
- `ImportExportService` - импорт и экспорт подключений.
- `Logger / LogSanitizer` - журналирование и удаление секретов из сообщений.

### Dependency rules

- UI не зависит напрямую от SQLite, QtKeychain или libsmb2.
- `RemoteFileModel` не вызывает libsmb2 напрямую.
- Repositories не зависят от UI.
- `SmbClient` не зависит от конкретных widgets.
- `Libsmb2SmbClient` является infrastructure detail и может быть заменен.
- `FakeSmbClient` используется в unit/integration-like tests без реального SMB.
- User-facing строки и локализация не должны протекать в infrastructure layer; backend возвращает error codes и sanitized details, а UI/application layer выбирает перевод.

### Асинхронность и thread-safety

- Все сетевые и длительные файловые операции выполняются вне UI thread.
- UI получает результаты через signals/slots, futures или другой Qt-friendly async mechanism.
- Cancellation token или эквивалентная abstraction должны передаваться в операции.
- Progress events должны быть thread-safe и доставляться в UI thread.
- Общие объекты repositories, client sessions и operation state должны иметь ясную ownership model.
- SMB-сессии не должны неконтролируемо использоваться из нескольких потоков, если backend не гарантирует thread-safety.

### Ошибки

Ошибки должны использовать типизированную модель, например `SmbErrorCode`, а не только строки.

Минимальные категории:

- None.
- InvalidPath.
- DnsError.
- ServerUnavailable.
- ShareUnavailable.
- AuthenticationFailed.
- PermissionDenied.
- Timeout.
- ProtocolUnsupported.
- NetworkError.
- FileNotFound.
- AlreadyExists.
- DirectoryNotEmpty.
- OperationCancelled.
- LocalIoError.
- CredentialStoreUnavailable.
- CredentialNotFound.
- Unknown.

Каждая ошибка должна иметь:

- Code.
- User-facing message.
- Sanitized technical details.
- Retryable flag при необходимости.
- Source module.

## Ошибки и статусы подключения

Статусы подключения в UI:

- Unknown.
- Not checked.
- Checking.
- Available.
- Server unavailable.
- Share unavailable.
- Authentication failed.
- Permission denied.
- Timeout.
- DNS error.
- Protocol unsupported.
- Error.

Поведение:

- "Check" переводит статус в Checking.
- Успех обновляет статус Available и `last_successful_check_at`.
- Ошибка обновляет status, `last_error_code`, `last_error_message`.
- Ошибки должны быть sanitized до сохранения и отображения в журнале.
- Проверка не должна запускаться автоматически для всех подключений при старте приложения.

## Логирование

Логирование должно поддерживать:

- Файл логов.
- Внутренний `LogViewer`.
- Уровни debug/info/warn/error.
- Категории: app, storage, credentials, smb, transfer, ui, import_export.
- Correlation ID для операций.
- Sanitization перед записью.
- Ротацию или ограничение размера логов.

Политика безопасности:

- Любой лог проходит через `LogSanitizer`.
- Секреты маскируются до попадания в файл и UI.
- Ошибки credential store не должны раскрывать пароль или master password.
- Экспорт с паролями логируется только фактом операции и путем назначения в sanitized форме, без содержимого.

## Packaging / distribution

Первая версия должна предусмотреть сборку и распространение для:

- Windows installer или portable package.
- Linux AppImage/deb/rpm как отдельное решение после базовой сборки.
- macOS app bundle/dmg.

Packaging должен учитывать:

- Доставку Qt runtime.
- Доставку libsmb2 и зависимостей.
- Доставку QtKeychain и зависимостей.
- Доставку translation resources для English/Russian UI.
- Подпись приложений, если требуется платформой.
- Хранение пользовательской SQLite базы в platform-appropriate app data directory.
- Хранение логов в platform-appropriate log/cache directory.

## Риски и открытые вопросы

- Полнота и стабильность libsmb2 на Windows, Linux и macOS для всех нужных операций.
- Поддержка current user auth через кроссплатформенный backend.
- Поведение guest/anonymous auth на разных SMB-серверах.
- Поддержка copy/move между разными SMB-шарами через backend без локального промежуточного файла.
- Семантика permissions/attributes может отличаться между Windows SMB и Samba.
- Drag-and-drop из SMB на рабочий стол может требовать временного локального файла и platform-specific DnD integration.
- Нужны ли encrypted exports в дополнение к plain-text export with passwords.
- Какую криптографическую библиотеку использовать для fallback vault.
- Нужен ли audit log для dangerous operations.
- Какая минимальная версия Qt5 и компиляторов поддерживается.
- Требуется ли переключение языка полностью без перезапуска для всех окон или допустим перезапуск для части UI первой версии.

## Критерии готовности первой версии

Первая версия считается готовой, если:

- Пользователь может добавить, отредактировать и удалить SMB-доступ.
- Пути и учетные данные нормализуются согласно требованиям.
- Метаданные хранятся в SQLite.
- Пароли хранятся через QtKeychain или fallback encrypted vault, но не в plain text SQLite.
- Проверка доступности запускается по кнопке и различает основные классы ошибок.
- Пользователь может открыть SMB-шару во встроенном браузере.
- Браузер отображает remote files через `RemoteFileModel`, а не `QFileSystemModel`.
- Базовые операции браузера работают: open folder, back, up, refresh, download, upload, create folder, delete, rename.
- Открытие файла скачивает его во временный кэш и открывает системным приложением.
- Логи пишутся в файл и доступны в `LogViewer`.
- `LogSanitizer` предотвращает попадание секретов в логи.
- Экспорт без паролей работает по умолчанию.
- Экспорт с plain-text паролями доступен только через явное подтверждение и предупреждение.
- UI не блокируется во время сетевых операций.
- Есть unit tests для core logic и tests with `FakeSmbClient`.
- Интеграционные Docker Samba tests выделены в optional profile.
- Приложение собирается CMake-проектом на целевых платформах или имеет подтвержденный план устранения платформенных blocking issues.
- Основной UI доступен на английском языке, русский перевод подключен и выбирается в настройках.
